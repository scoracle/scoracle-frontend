# Fix SSR-side fetch firing on the default-active tab

**Date:** 2026-04-26
**Scope:** Hotfix for a regression introduced by the combined effect of two earlier commits in this session: `4b90c16` (drop `clientOnly` on the cards) and `78f4df7` (collapse `shouldLoad` ladder via `createMemo`). On a fresh `/profile` page load the user saw "Couldn't load the News card. HTTP 403." with a Try Again button that always succeeded.

## Goal

Restore the invariant the audit assumed: tab data fetches happen on the client only, never on the SSR pass.

## What Went Wrong

Before this session, the tabs used:

```text
const [shouldLoad, setShouldLoad] = createSignal(false);
createEffect(() => { if (props.active() && !shouldLoad()) setShouldLoad(true); });
const [data] = createResource(shouldLoad, fetchNews);
```

`createEffect` does not run on the SSR pass — Solid intentionally skips effects on the server. So `shouldLoad` stayed `false` during SSR, the resource never fetched, and the SSR pass produced just the loading skeleton.

The `createMemo` collapse in commit `78f4df7` swapped the latch to:

```text
const shouldLoad = createMemo<boolean>(prev => prev || props.active(), false);
```

Memos *do* run on SSR (that's what makes them deterministic across server/client). The default tab (`NewsTab` when `view='news'`, the URL default) had `props.active() === true` on the SSR pass, so the memo returned `true`, and `createResource` fired the fetch from inside the Cloudflare worker.

The Go API at `api.scoracle.com` returned 403 to the worker-originating request (server-to-server, no browser Origin, possibly WAF). SolidStart serialized the resource error into the HTML payload. On client hydration the `ErrorBoundary` saw the carried-over error state and rendered the "Couldn't load…" fallback. "Try Again" reset the boundary; the retry was a clean client-side fetch and succeeded.

## What Was Done

Added a `!isServer` clause inside the `createMemo` in all six tabs. Source pattern:

```text
const shouldLoad = createMemo<boolean>(
  prev => prev || (!isServer && props.active()),
  false,
);
```

`isServer` (from `solid-js/web`) is `true` during SSR rendering on the server and `false` in the browser. The `&&` short-circuits on the server so the memo can't latch true there; on the client the `!isServer` is always true and the latch behaves identically to before.

This puts the gate in one place per tab — no need to also gate `createResource(shouldLoad, fetcher)` separately.

## Verification

- `npm run typecheck` — green.
- `npm run build` — green.
- `npm test` — 67/67 passing (the data-utility tests aren't affected; this is purely a render-time gate).
- Dev server: `curl http://[::1]:<port>/profile?sport=NBA&type=player&id=1` → SSR HTML is 60 KB, contains the loading skeletons, and crucially does **not** contain the `card-error` class anywhere — proving the resource never errored on SSR. With the bug present, the same SSR HTML showed an SSR-rendered `<div class="card-error" role="alert">` block.

## Result

The 403 is gone. SSR HTML now ships the loading skeleton; the client takes over after hydration and fires the fetch with browser headers. EntityMeta (which I'd already gated via `() => !isServer` directly on its `createResource` source in commit `4b90c16`) and the six tabs are now consistent: all fetches are client-only.

## Note on the second user-reported issue

The user also reported visible flicker when clicking "Statistical Profile" (the toggle that flips to the Stats card) and the "Vibes" tab. That is a *separate* tradeoff — the audit's finding #2 (the lazy-load gate via `cardActive`) trades a fetch on the hidden card for a brief skeleton on the first flip. It's not a bug. Different fix-paths exist (revert the gating, prefetch on hover, eagerly warm on profile mount). Not addressed in this commit; awaiting product input.
