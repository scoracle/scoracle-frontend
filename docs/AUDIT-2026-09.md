# Frontend Audit — Solid 2 & Eager Loading

Date: 2026-09-27
Stack: `solid-js@2.0.0-rc.8`, `@solidjs/web@2.0.0-rc.8`, `@solidjs/router@2.0.0-next.24`,
`@solidjs/meta@1.0.0-next.2`, `vite@8.3.0`, `@solidjs/vite-plugin@3.0.0-next.35`.
Framework is `ssr: true` + `serverFunctions: true`, deployed to Cloudflare Workers.

## Philosophy: "eager load everything"

The stated target is **eager**, not lazy. That inverts the usual audit. The following are
**intentional and must not be "fixed"**:

- No `lazy()` / `import()` code splitting anywhere. `src/app.tsx:6-18` statically imports
  all 12 routes; the build emits a single 288 KB raw / **93 KB gzip** entry chunk plus a
  75 KB CSS chunk. One blocking request, no waterfall.
- `src/components/solid/card-registry.tsx:23-29` eagerly imports all 7 card components,
  and `src/components/solid/ReadingTable.tsx:56-58` mounts every pane eagerly on purpose —
  this keeps `?tab=` navigation instant and keeps the crawler view complete.
- Every requester receives fully-rendered HTML (`README.md:22-28`).

**The philosophy shifts the question**, from "should this be deferred?" to:

1. Is everything eager actually loaded *early*, and in the *right variant*?
2. Is the eager cost paid *once*, or repeatedly at runtime?
3. Does eager SSR render bugs that a lazy app would have hidden?

A size **ceiling** (not a split) is the control that keeps the monolith intentional.
`scripts/verify-build.mjs` currently has none, and `vite.config.ts` has no `build` block.

## Baseline: Solid 2 idioms are genuinely strong

This is not a Solid 1 app with a bumped version. Zero 1.x APIs survive:

- No `createResource`, `Suspense`, `Index`, `mergeProps`/`splitProps`, `batch`, `on()`,
  `createComputed`, `startTransition`, `createSelector`, `produce`, `onMount`, `classList`,
  `attr:`/`on:`.
- Async is expressed as `createMemo(async …)` + `<Loading>` / `<Errored>` (the RC8
  replacements for `Suspense`).
- Props are **never destructured**; call sites pass values, not accessors. `splitProps` /
  `mergeProps` are absent and not needed.
- All 15 `createEffect` sites use the correct 2-arg compute/apply form, four with
  `{ defer: true }`.
- `onSettled` (the `onMount` replacement) is used correctly, often returning cleanup.
- No handrolled lazy patterns: no `IntersectionObserver`, no `import()`-in-effect+`setState`,
  no custom `defineAsyncComponent`.
- No charting/map/editor libraries at all — charts are hand-rolled SVG over pure math in
  `src/lib/charts/`. Nothing heavy to split.

## Load-bearing constraint

`scripts/patch-solid-ssr.mjs:4` **hard-fails on any version other than `2.0.0-rc.8`**,
string-patching two promise-lifecycle sites in `@solidjs/web/dist/server.js` /
`server.dev.js`. Eager SSR makes this more critical, not less. `npm run verify:build` is
the gate on any Solid bump, and no work below should land without it passing.

## Tier 1 — Eager-load correctness

Gaps that the eager philosophy itself exposes.

### T1.1 Dead font payload — 506 KB of unreferenced CDN weight
`src/global.css:13-27` declares exactly two `@font-face` rules (both correctly
`font-display: swap`), referencing only `fraunces-var.woff2` and
`fraunces-italic-var.woff2`. Four files in `public/fonts/` are referenced **nowhere** in
`src/`:

| File | Size |
| --- | --- |
| `fraunces-latin-full-normal.woff2` | 121 KB |
| `fraunces-latin-full-italic.woff2` | 150 KB |
| `fraunces-latin-ext-full-normal.woff2` | 105 KB |
| `fraunces-latin-ext-full-italic.woff2` | 130 KB |

Under eager-everything, unrequested bytes are pure loss. Delete them.

The comment at `src/global.css:10-12` claims the roman cut is preloaded "in
entry-server.tsx"; the preload actually lives at `src/Document.tsx:30`. Fix the pointer.

### T1.2 Atmosphere backdrop competes with the LCP hero for bandwidth
`src/components/solid/PageAtmosphere.tsx:19` renders as a fixed, `aria-hidden` backdrop at
`opacity: 0.32` (dark: 0.16), with `decoding="async"` but **no `fetchpriority`**. It is a
130–149 KB file that is deliberately *not* the LCP element, yet the browser schedules it at
default priority and competes with the real hero (`CrystalBall.tsx:124`, which correctly sets
`fetchpriority="high"`).

Fix: `fetchpriority="low"`. This keeps the eager load (one composition, unchanged) but stops
it starving the LCP image. No CSS change needed.

Measured route coverage: the atmosphere is on `/` and `/leaderboard` only — **not** on
`/profile`, `/stories`, or the legal pages. Correct the "every route" assumption; the change
is still right, it just touches 2 routes.

**Do not add `srcset` or `<picture>`.** Three mobile variants exist in `public/images/`
(`impasto-drapes-threaded-mobile-3.webp`, `-mobile-5.webp`, `-mobile-default-5.webp`) but
they are **deliberately unused**:

- They are **768×1152 portrait**, versus the desktop **1536×1024 landscape**. They are an
  art-directed *recomposition* ("user-directed vertical-strand mobile revision" per
  `impasto-drapes-threaded-mobile-5.sources.json`), not a downscale — so `srcset` width
  descriptors would be wrong and would distort the crop.
- `PageAtmosphere.test.tsx:13` explicitly asserts `wash.querySelector("source")` is `null`
  in a test named *"keeps the default drapes decorative and **uses one composition at every
  size**"*. The one-composition decision is test-locked.

The component renders two `<img>` (`left`/`right`) with the **same** `src`, so the browser
dedupes to a single request per pageview.

### T1.3 The LCP hero is a 361 KB PNG — ship a WebP twin
**This replaced the original "add a preload" finding, which was wrong.**

`/images/scoracle_crystal_ball.png` is **1378×1309 RGBA, 360,992 bytes**, referenced only at
`src/routes/index.tsx:39`, and it is the home page's LCP element. Every other raster the site
serves is already `.webp`. Under eager-everything, shipping PNG to browsers costs ~230 KB of
avoidable transfer on every home pageview.

Fixed by deriving `scoracle_crystal_ball.webp` (130,172 bytes, **-63.9%**, same dimensions,
alpha preserved) via `scripts/build-hero-webp.mjs`, wired into `npm run build` so it can never
drift from its source.

**The PNG must stay.** It is not a redundant duplicate:
- `scripts/sync-token-assets.mjs:28` syncs it from `@scoracle/tokens` (`brand/scoracle-crystal-ball.png`),
  and `npm run check:assets` enforces that mapping.
- `scripts/build-orb-mask.mjs:26` cuts the orb glass/rim/silhouette masks **from it**, with a
  flood-fill tuned to this asset's exact pixel coordinates (`CX = 628`, `CY = 729`, "All masks
  share the original art coordinates").

So the PNG is the canonical art and the mask pipeline's source; the WebP is a delivery-only
twin. `build-hero-webp.mjs` asserts dimensions and alpha on every build to keep that honest.

**No preload added, deliberately.** `Document.tsx` is shared by all 12 routes, and the hero is
home-only — a global `<link rel="preload" as="image">` would pull 130 KB on every leaderboard,
profile, story, and legal pageview. The `<img>` is already `loading="eager"`
`fetchpriority="high"` and is SSR'd early in `<body>`, so the size reduction is the real win.

### T1.3 No preload for the LCP hero
`src/components/solid/CrystalBall.tsx:124` correctly sets `loading="eager"` +
`fetchpriority="high"`, but the image is only discovered mid-HTML-parse. Add the matching
`<link rel="preload" as="image">` to `src/Document.tsx`.

### T1.4 `deck-art/` — 3.0 MB with no priority control
`src/components/solid/Card.tsx:167` and `src/lib/cards/deck-illustration.ts:32` load these
through inline-style CSS `url()`. Browsers assign CSS-background images low priority and
they cannot be preloaded per-card. Consider a preload hint for the first-rendered card's
art. Note the same trap as T1.3: a preload must be scoped to the routes that actually show
the card, not added globally to `Document.tsx`.

### T1.5 No size ceiling
Add a size budget to `scripts/verify-build.mjs`. Nothing currently fails the build on
bundle growth, so the monolith can drift without anyone noticing. Baseline to hold: entry
chunk **288 KB raw / 94 KB gzip**, CSS chunk **77 KB raw / 15.5 KB gzip**.

### Running the browser suite

`npm run test:browser` is **not** broken — it just has a hard local-backend prerequisite
that is not documented. `scripts/api-proxy.mjs` is a real pass-through: it fetches
`http://127.0.0.1:18000/api/v1/...` and returns **502** when nothing is listening there. The
app's designed behaviour converts API failure into a **503** page, and Playwright's
`webServer` health check requires 2xx/3xx, so it times out before any test runs. The
502→503→timeout chain makes this look like a test bug; it is a missing tunnel.

The working invocation:

```sh
ssh -f -N -L 18000:127.0.0.1:8000 archbox   # archbox runs the scoracle-api Go service on :8000
npx playwright install chromium             # headless shell was not downloaded
SCORACLE_TEST_WORKERS=1 npm run test:browser
```

Two latent config issues surface along the way, both pre-existing:
- `playwright.config.ts` passes `SCORACLE_INTERNAL_KEY` via `--var`, but wrangler wants a
  secret, so it logs *"Missing required secrets"* on every run.
- The default branch (`SCORACLE_TEST_WORKERS` unset) runs `vite preview`, which cannot
  serve a Workers SSR app at all. Only the wrangler branch works.

Worth fixing so this stops being tribal knowledge: document the tunnel in `README.md`, and
either correct the secret wiring or drop `SCORACLE_INTERNAL_KEY` from the required list.

## Tier 2 — Stop paying the eager cost twice

Deliberately paying full parse + full hydration makes paying it *again at runtime* the
actual sin. These get **more** important under this philosophy, not less.

### T2.1 `<For>` keyed on fresh object identity — silent full rebuild
`<For>` default-keys on item identity. These sources hand it **new objects every
recompute**, so every row is destroyed and recreated:

- `src/routes/leaderboard.tsx:752` — `<For each={rows()}>` with no key, and `rows()` at
  `:444` does `.map(r => ({...}))`. Every revalidation rebuilds all 50 `<li>`, each with
  nested `<Show>` fallbacks and a `<GemmaSummary>`. Fix: `keyed={r => r.href}`.
- `src/components/solid/Select.tsx:73` — every caller builds options with `.map`
  (`ReadingTable.tsx:179,187-191,217`; `leaderboard.tsx:402-437,586,714-717`). Fix:
  `keyed={o => o.value}`.
- `src/components/solid/NavWell.tsx:96` — fed by `navItems()` (`.map` → new objects). Worse,
  the marker-placement effect at `NavWell.tsx:91` lists `props.items` in its explicit deps
  by **array identity**, so it re-runs rAF + `getBoundingClientRect` on any recompute even
  when no label changed. Key the `For` by `item.id` and depend on
  `props.items.map(i => i.id)`.
- `src/components/solid/CompareControl.tsx:29` — `selected()` allocates a new object per
  read (harmless today, unstable for any future keyed consumer).

Contrast (already correct): `TransfersCard.tsx:53` and `NarrativesCard.tsx:50` re-sort but
keep **identical item identities**, so `<For>` diffs properly; `ButterflyChart.tsx:110` /
`PizzaChart.tsx:164` reorder the same objects.

### T2.2 `Array.from` as a list renderer — no diffing at all
- `src/components/solid/Board.tsx:116` — `Array.from({ length: count() }, ...)` rebuilds
  every row on every recompute. RC8's `<Repeat count={count()}>` is the exact primitive
  (`i` is a plain number there, matching the current use).
- `src/components/solid/EntityMeta.tsx:61` — `Array.from` plus a now-redundant
  `keyed={false}` (the `keyed={false}` usage itself is correct RC8; the `Array.from` makes
  it pointless).

### T2.3 Duplicate computation graph on the hydration critical path — **ATTEMPTED TWICE, REVERTED**
`src/lib/data/profile-data.ts` (`useProfileRead` = `createMemo(useProfileReads()[key])`) and
`src/lib/cards/deck-scores.ts` (`createDeckScoreReader`) each wrap the same `query()` key in
their own `createMemo`; `EntityMeta.tsx` creates a **third** for the same read. `query()`
dedupes the *network* but not the *computation graph* — ~2× the nodes, and two independent
`NotReadyError` paths plus two `isPending` behaviours for one logical value.

**This was attempted a second time (2026-09-27) with a cold-start guard in place first, and
reverted again for a different and more fundamental reason.**

Attempt: a new `memoProfileReads()` at the provider gives each read key exactly one
computation shared through context. `useProfileRead` and `createDeckScoreReader` then stop
creating their own.

**First blocker — cold-start card loss (known from the first attempt).**
`deck-content.ts` (`deckHasContent`) `await`s each read inside its own per-card async
boundary. Reading a shared memo from inside that nested async subjects it to the shared
computation's readiness, and on a cold cache the `NotReadyError` escaped into
`ReadingTable.tsx`'s `.catch(() => true)` presence classification. Dealt-tab membership then
depended on whether `query()` happened to be warm — i.e. **the first visitor of a cold Worker
got an incomplete profile page**, with no error and no 5xx. Fixed within the attempt by giving
`deckHasContent` RAW reads (`profileReads(ctx)`) instead of the shared accessors.

**Second blocker — error isolation, which is a documented requirement.**
With presence fixed, three browser tests failed: *backend deadline yields a card error while
sibling cards survive*, *a failed shared score product stays isolated*, and *a slow new route
immediately replaces the departing page with its skeleton*. All three are failure-isolation
and pending-state assertions.

This is not incidental. `createDeckScoreReader`'s own docstring states the contract:

> *"Isolate errors per reader so one deck's outage cannot drop the other readings."*

The per-consumer `createMemo` **is** that isolation. One memo per key means a failed read
fails every consumer of that key at once — the card, the ring, and the score reader together —
which is the precise behaviour those three tests exist to prevent. Sharing the memos would
have to remove a documented guarantee to work, so it is not a refactor; it is a behaviour
change that needs its own design and test pass.

**What was kept:** `verify:ssr` now pins the dealt tab set exactly
(`deckTabs: ["Vibe", "Momentum", "Sigil"]` on the fixture profile). The browser/crawler parity
check only proves two renders agree with each other — it cannot catch a cold-cache render that
drops cards on *both*. The new assertion can, because the first route rendered in a
`verify:ssr` process is a cold one. It was verified to fail loudly when the hazard is
reintroduced.

**Still open,** but now with the reason correctly identified: sharing would need the score
readers to keep their isolation (e.g. a shared *resolved value* that each reader wraps in its
own error boundary), not a single shared computation. That is a design task, not a cleanup.

### T2.3b `ReadingTable.tsx:104-108` — handrolled keyed presence table — **NOT ATTEMPTED**
```ts
const presence = new Map(CARD_REGISTRY.map(tab => [tab.id,
    createMemo(() => ctx.week() ? false : deckHasContent(ctx, data, tab.id).catch(() => true)),
]));
```
Seven independent async computations with per-deck error policy, built eagerly in the
component body and read through a `Map` lookup. RC8's `createProjection(…, { key: "id" })`
is the migration target (`createSelector` is gone). **Deliberately left alone for now** —
this is the same presence-classification code path that T2.3's revert exposed as
cache-warmth-sensitive. Migrating it while that hazard is unaddressed risks the same
cold-start card loss. Do it together with the T2.3 follow-up, behind a cold-start
`verify:ssr` assertion.

### T2.4 Plain closures that re-derive on every read — **DONE**
- `src/components/solid/GemmaSummary.tsx:55-56` — `paragraphs()` re-split the whole prose
  string per read, and was read twice per render (`:58` `each`, `:61` `last()`). Now a
  `createMemo`.
- `src/components/solid/ProfileCard.tsx:63-96` — seven plain closures; `pizzaStats()` is
  called at `:99` (in `when=`) and `:108` (as a prop), and allocates a new array of new
  objects each time.
- `src/routes/leaderboard.tsx:371-441` — nine closures; `scopedTeamEntities` is O(n) inside
  three option builders, each read from a `<Show when={… .length > 1}>` → 4+ full
  directory passes per render.
- `src/components/solid/TransfersCard.tsx:28-30`, `NarrativesCard.tsx:27-29` — copy + sort +
  slice per read. Both now `createMemo`, which also pins item identity so their `<For>`
  diffs instead of re-keying on a fresh array.
- `src/components/solid/ProfileCard.tsx` — `pizzaStats()` and `filteredPizzaDatapoints()`
  now `createMemo`. `pizzaStats` was the sharpest case: it built a brand-new array of
  brand-new objects per read AND was read twice per render, so `<PizzaChart>`'s keyed
  diffing saw every wedge as changed on every pass.
- `src/routes/leaderboard.tsx` — `teamEntities()` / `playerEntities()` filter+sort the whole
  sport directory per read, and four option builders each read them (4+ full directory
  passes per render). All six now `createMemo`; the stable array identity also helps the
  newly-keyed `Select`.

## Tier 3 — Real bugs, philosophy-independent

### T3.1 SSR/client timezone divergence — **DONE (real bug, regression-tested)**
`src/components/solid/WeekCard.tsx:30-39` formats with local `getDay()` / `getHours()` on a
`new Date(iso)`, and `src/lib/utils/date.ts:17-27` (`formatDate`) uses
`toLocaleDateString` with no `timeZone`. Server is UTC (Cloudflare), client is the viewer's
TZ. `src/components/solid/MomentumCard.tsx:38-42` already pins `timeZone: "UTC"` for
exactly this reason, so the two files disagree. Eager SSR makes this guaranteed, not an
edge case. Affected SSR output: `WeekCard` (week-archive mode), `StoriesBoard.tsx:54`,
`story/[id].tsx:63,120-124,174,246,269`.

Reproduced concretely for `2026-09-27T02:30:00Z`:

| Renderer | `dayLabel` | `formatDate` |
| --- | --- | --- |
| Server (Cloudflare = UTC) | `Sunday · Sep 27` | `Sep 27` |
| Client, America/New_York | `Saturday · Sep 26` | `Sep 26` |

Wrong day-of-week *and* wrong date for every viewer west of Greenwich.

Fixed by pinning UTC at both sites: `date.ts:formatDate` now passes `timeZone: "UTC"`, and
`WeekCard.dayLabel`/`timeLabel` use the `getUTC*` accessors. `formatDate` deliberately
keeps `toLocaleDateString` rather than switching to a cached `Intl.DateTimeFormat`, so its
documented `"Invalid Date"` behaviour for garbage input is preserved.

The pre-existing test at `date.test.ts:5-11` had **worked around** this bug by choosing
`12:00:00Z` timestamps "so the output doesn't drift across CI timezones". Replaced with a
guard that uses `02:30:00Z` and asserts the UTC day — verified to **fail** against the old
unpinned implementation (`expected 'Sep 26' to be 'Sep 27'`) in this repo's
`America/New_York` dev/CI zone.

### T3.2 Async reads outside their own `<Loading>` — boundary escalation — **DONE (2 of 3 demonstrable)**
The app's async-memo idiom only behaves well when the read sits under a *scoped* boundary.
Three places leak to an outer, coarser one:

- `src/routes/leaderboard.tsx:340` — `sportWeeks` is read via `weekSelectOptions()` at
  `:725`, which sits outside the filters' `<Loading>` (`:690-706`) but inside the
  whole-board `<Loading>` (`:678-797`). A pending `/weeks` read replaces the **entire
  board**. `scopeEntities` / `scopeTeamMeta` at `:369-370` already do this correctly with
  `loadingValue`.
- `src/routes/index.tsx:32,39,44` — the home "movers" carousel has no local `<Loading>`, so
  it escalates to `app.tsx:45`'s `PageSkeleton` and holds the entire home page (wordmark,
  ball, search). `.catch(() => [])` also means failure can never surface — silently empty.
- `src/routes/profile/index.tsx:38-42,129-131` — the directory's per-sport strips escalate to
  the app-level boundary; the whole `/profile` directory shows `PageSkeleton` until all six
  leaderboard reads settle.

The **profile route** is the model to follow: `profile/[id].tsx:254-280` has one
`<Loading on={entityKey()}>` over meta + table, a second for the atmosphere, a nested
`<Errored>` around `ReadingTable`, and each card then owns its own boundary.

Fixed by giving each read its own boundary:

- `routes/index.tsx` — the hero region (ball + search) now sits in a local `<Loading>`, so a
  pending movers feed shows a bounded placeholder instead of replacing the wordmark, ball
  and search with the app-level `PageSkeleton`. Fallback copies the ball's own box
  (`.crystal-art` is 1378/1309 capped at 560px, plus its 768/480 breakpoints) so the search
  beneath it does not shift. `loadingValue: []` was **not** used: it would also swallow the
  SSR pass, and `verify:ssr` contractually requires the first mover in the initial HTML.
- `routes/profile/index.tsx` — each `SportDirectory` gets a `<Loading>` inside its existing
  `<Errored fallback={null}>`, with a fallback that keeps the strip's box and names the
  sport. The browse page now composes while the three strips fill.
- `routes/leaderboard.tsx` — the week `<Select>` gets a local `<Loading fallback={null}>`.

**Honest caveat on the leaderboard one: that is defense-in-depth, not a demonstrated bug
fix.** A fault-injected browser test could not distinguish the fixed from the unfixed build,
because `preload()` (`:124`) already warms `getWeeks(sport)` on client navigation, so the
read is not observably pending when the `<Select>` renders. The boundary still matters for
revalidation and error-recovery paths that bypass intent preload, and it matches the pattern
the same file already uses for the cohort filters — so it stays, but it is not the
user-visible win the other two are.

### T3.3 Phantom test mock — **DONE**
`src/components/solid/Card.test.tsx:9-12` mocks `createAsync` from `@solidjs/router`. That
export **does not exist** in `@solidjs/router@2.0.0-next.24` (its data entry exports only
`action`, `useSubmissions`, `useAction`, `query`, `revalidate`, `liveQuery`), so the mock is
a no-op leftover from a pre-RC alpha. Worse, `Card.tsx` never imports from
`@solidjs/router` at all, so the mock stubbed a module the component does not use. Deleted;
7/7 in the file still pass.

### T3.4 Top-level reactive reads in component bodies — **DONE**
`src/components/solid/EntityMeta.tsx:34` and `src/routes/stories.tsx:11-18` — the last two
remaining (dev-warned in Solid 2). `stories.tsx` snapshots `searchParams` once and never
updates.

- `stories.tsx` built the redirect target in the component body from a one-time
  `searchParams` read, so a `?sport`/`?status` change while already on `/stories` left the
  redirect pointing at the destination it was built from. `RouteRedirect` was already
  correctly reactive (`createEffect(() => props.href, …)`) — it was being handed a frozen
  value. The target is now a `createMemo`.
- `EntityMeta.tsx`'s `if (!ctx.sport() || !ctx.id()) return null` bail is now a `<Show>`,
  so the guard is a flow dependency instead of a read that evaluated once at setup and
  could not react if the route params changed without a remount.

### T3.5 Inconsistent head-tag boundary ownership — **DONE**
`src/routes/profile/[id].tsx:210-239` reads `meta()` (`:197`) **outside** any route-level
`<Loading>`; the nearest boundary is `app.tsx:45`. `src/routes/story/[id].tsx:142-146` puts
identical `<Title>`/`<Meta>` tags **inside** its `<Loading on={…}>` (`:140`). A client-side
entity change on the profile route therefore resolves head through the app-level
`PageSkeleton`.

Fixed: the head fragment now sits in `<Loading on={entityKey()}>`, matching the story route,
so head resolution is governed by the route's own entity boundary. `entityKey()` is also
now a `createMemo` — it feeds three `<Loading on={…}>` scopes and as a plain closure each use
rebuilt the template string and re-read all three signals to hand `<Loading>` a value it only
ever compares.

## Tier 4 — Solid 2 idiom alignment

**Shipped:** T4.1 dead `onCleanup` imports (Disclosure, NavWell, PizzaChart, ButterflyChart) ·
T4.2 four manual class strings → array form (Skeleton, GemmaSummary, AdSlot, ButterflyChart;
`PageAtmosphere` was already done in T1.2) · T4.3 `<Match when={true}>` → `Switch`'s `fallback`
· T4.4 redundant `untrack` · T4.5 Disclosure's two same-dep effects merged into one ·
T4.6 `ReadingTable`'s two component-lifetime `onCleanup`s → `onSettled` returns ·
T4.7 `CardVessel`'s five-branch host switch → `<Dynamic>` · T4.8 `NavWell` presence check →
`children()` and `AppTray`'s handrolled icon registry → `dynamic()` · seven unused context
destructures dropped across six cards.

**Two items deliberately NOT done, with reasons:**

- **`SearchBar`'s `mounted` signal → `ssrSource: "client"`** *(my own earlier suggestion —
  withdrawn after reading the types). `ssrSource` is a field on `MemoOptions`
  (`node_modules/solid-js/types/client/hydration.d.ts:35`): it selects the hydration value
  source and whether an **async** compute re-runs. It is not a mount gate. Applied to a signal
  it would mean "client uses its initial value immediately" — the exact opposite of the gate,
  and it would reintroduce the mismatch the flag prevents. `onSettled(() => setMounted(true))`
  is already the correct, explicit expression of "false through SSR and the first client
  render, true after".
- **`<Reveal>` for the sibling boundary groups.** It "coordinates the reveal timing of sibling
  `<Loading>` boundaries" — progressive reveal. `entry-server.tsx` deliberately `await`s
  `renderToStream` to return settled HTML, so during SSR every boundary has already resolved
  and there is nothing to coordinate. On the client `order="sequential"` would hold the deck on
  its fallback until the decorative `PageAtmosphere` resolves — making primary content wait on
  decoration, and contradicting browser tests that pin the current skeleton behaviour. Adding
  it would be a UX regression dressed as an idiom upgrade.

### T4.7 `CardVessel` → `<Dynamic>` — the one that needed proving
The switch carried the note *"Static host branches keep child hydration IDs aligned on Solid 2
RC"*, and `CardVessel` is the most-used primitive in the app, on a runtime whose SSR internals
are already patched by `scripts/patch-solid-ssr.mjs`. So this was re-tested rather than assumed:
221 unit tests, full `verify:ssr` browser/crawler parity, and 20/20 browser tests all pass, and
the SSR output still carries correct host tags (profile renders `article` ×6 + `div` ×1 for the
meta vessel, `card-foot-name` ×7, no `undefined` leakage). The comment was stale — written for
an earlier RC. As a bonus the host is now genuinely reactive in `as`, which the `switch` in a
component body never was.
